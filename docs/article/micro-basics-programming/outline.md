## 章別計画

各章で、先にテストを書く関数と、テストの期待値です。期待値は、マインドマップに書かれた値と、手計算で確かめた**例**です。下の数値は、計画の時点で、スクラッチで実測して確かめた値です。実装時に、再確認します（マインドマップの値の誤りも、疑います）。

**章をまたいで使う数値**（予想の効果を高めるため、使い回します）:

- 消費者: U = x·y、Py = 1、所得 m = 80。Px = 2 で、最適消費点は (x, y) = (20, 40)、U = 800
- 企業: 総費用 C = q³ − 6q² + 15q + 32（固定費用 32）。MC の最低点は q = 2（MC = 3）、AVC の最低点は q = 3（AVC = 6）、AC の最低点は q = 4（AC = 15 = MC）
- 市場: 需要 Q = 100 − P、供給 Q = P − 10。均衡は P = 55、Q = 45

## 学習設計

マクロ初級と同じ設計（メンタルモデル構築ガイドの 5 フェーズ）を、そのまま引き継ぎます。

### 章の型

全章を、同じ節の構成（準備を含めて 9 節。到達チェックの章は 10 節）にそろえます。

| 節 | 内容 |
| :--- | :--- |
| この章の地図 | 題材・使う機能・完成形のファイル・式とコードの対応表。**図を 1 点、先に見せる** |
| 予想する | コードを見る前に、結果を予想する。**答えは書かない** |
| 概念の説明 | その章で使う経済学の用語と、ライブラリの機能 |
| プログラミング | テストを先に書き、最小の実装で通し、整える。**小節「予想の答え合わせ」**で、予想の答えを、プログラムで確かめる。図の描画テストは、折りたたむ |
| 規則で言うと | 原則 2〜3 個、混同しやすい対比の表（マインドマップの「混同注意」）、「このモデルが成り立たない場面」 |
| 練習問題 | 想起・生成・多様・交互を各 1 問。解答は、問題の下に折りたたむ |
| 振り返り | うまくいったこと、詰まったこと、次に試すこと |
| まとめ | 学んだことの確認と、次の章の予告。最終章は、次に読む連載の案内 |

マインドマップの「核の式」「混同注意」「描いて確認」を、「この章の地図」「規則で言うと」「プログラミング（図）」に、そのまま使います。

### 部ごとの到達チェック

先に「何も見ずに書く課題」を置き、答えが並ぶ表は、そのあとに置きます（マクロ初級のレビューで、順序の指摘がありました）。

| 部 | 何も見ずにできること | 検証の方法 |
| :--- | :--- | :--- |
| 1（第 4 章） | 無差別曲線と予算線から最適消費点を求め、需要曲線・弾力性・スルツキー分解を計算する | 最適点 (20, 40)、MRS = 価格比。価格効果 60 = 代替効果 20 + 所得効果 40。自作の関数が、章末のテストを通る |
| 2（第 7 章） | 費用曲線の 3 本の関係を言い、利潤最大化の数量・損益分岐点・操業停止点を求める | MC の最低点 q = 2、AVC の最低点 q = 3、AC の最低点 q = 4。P = 30 で、q = 5、利潤 68 |
| 3（第 10 章） | 均衡・余剰・課税の死荷重・関税の効果を計算する | 総余剰 2025、死荷重 20.25、関税の死荷重 100（三角形 2 つ） |

### 落とし穴への対策

| 落とし穴 | 記事での対策 |
| :--- | :--- |
| 読んで「わかった」と感じて終わる | 予想する節（答えなし）と、本文を閉じて書く課題を、必ず置く |
| 曲線の向き・傾き・面積を、取り違える（限界収入は需要の 2 倍の傾き、死荷重の三角形、関税は三角形が 2 つ） | 式・コードの対応表を、各章に置く。向きと面積は、テストで固定する。「混同注意」の対比の表を、本文に入れる |
| 最低点・交点の位置関係（MC は AC・AVC の最低点を通る、損益分岐点と操業停止点）を、取り違える | 同じ費用関数の数値例（q = 2・3・4）を、複数の章で使い回し、テストで固定する |
| グラフの意味が、式だけでは、つかめない | 曲線・シフト・均衡・余剰の図を、各章に入れる。描画関数の座標を、テストで確かめる |
| ゲーム理論の「均衡」を、最善の結果と取り違える | 囚人のジレンマで、ナッシュ均衡が、両者にとって最善でないことを、利得で示す |
| モデルの前提（完全競争、完全情報、取引費用なし）を、忘れる | 各章の「このモデルが成り立たない場面」に、前提を書く |

## 4 つの連載の教訓の反映

4 つの連載の全体レビューと、`creating-article` スキルの落とし穴を、最初から、計画に組み込みます。

## 記事とサンプル実装の整合の検査

共通パッケージ `apps/article-tools/` の検査を、そのまま使います。シリーズ固有の設定（図の一覧・解答の前提・抜粋）は、`tools/` に置きます。

| 検査 | 内容 |
| :--- | :--- |
| コードがフェンスの中にあること | 転記したコードが、コードフェンスの外に、出ていないか |
| 記事のコード例と実装の照合 | 記事の関数・クラス・定数のコードが、`lib/` と `test/` に含まれているか |
| 実行結果の件数の照合 | 各章の「実行結果」の `N passed` が、その章のテストの件数と一致するか |
| 解答のコードの実行 | 練習問題の解答に書いたコードを、実際に実行する |
| 予想の答え合わせの実行 | 小節「予想の答え合わせ」のスクリプトを実行し、記事の出力と一致するか |
| 図の検査 | 図のデータの指紋が、保存した値と一致するか、画像が、孤立していないか |
| 図の規則（シリーズ固有） | 全図に、凡例と、動かした曲線の線種の規則を課す（`test/tools/test_figure_style.py`） |
